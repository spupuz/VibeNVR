# Camera event providers

Camera-native events use `CameraEvent` in `backend/camera_event_provider.py`. A provider emits a generic event type, `active`/`inactive` state, source, and optional normalized labels. Only motion events enter the recording pipeline; other Hikvision smart events can be parsed without generating clips. Recording mode and pre/post-capture settings remain independent of provider selection. Configure the source and its status in the camera's **Event Sources** tab; the **ONVIF** tab is for device management and stream discovery.

`event_provider` is `server`, `onvif`, or `hikvision_isapi`. Existing cameras with no saved provider keep their former detection choice (`ONVIF Edge` maps to ONVIF; otherwise server). `backend/camera_event_coordinator.py` updates the selected provider when camera settings change. Exactly one camera-native provider is subscribed per camera. Selecting ISAPI never silently switches to ONVIF if the stream disconnects.

The Hikvision provider in `backend/hikvision_event_service.py` connects to the configured camera host on HTTP port 80 by default (the ONVIF port can differ). In Event Sources, choose explicitly whether to reuse ONVIF credentials or enter a complete separate ISAPI username/password pair. Existing cameras retain their saved settings. It uses HTTP Digest authentication, bounded multipart parsing, bounded reconnect delay, and redacted diagnostic error categories. It normalizes `VMD` human/person/pedestrian to a motion event labelled `person` and car/vehicle to `vehicle`. A camera should be configured to send VMD alarms through its ISAPI alert stream. Other smart-event types currently do not trigger clips.

New Hikvision motion clips can be cleaned up after they close. Enabled by default with a per-camera opt-out in Event Sources, the backend samples at most the last 30 seconds of the finalized video at low resolution. It trims only a confidently quiet tail beyond the configured Captured After duration. Ambiguous or failed analysis leaves the original video intact. Successful candidates are remuxed and validated in a temporary file beside the original, then atomically replaced before thumbnail generation, storage routing, and Timeline timestamps. Continuous recording and other event providers are unaffected.

The encoded packet ring used for passthrough pre-capture now follows Captured Before (up to its existing 10-second memory cap), including camera configuration updates. Actual pre-capture may be shorter when a camera does not provide a keyframe within that window.

The engine accepts validated normalized motion events, tracks active/inactive state and labels. For ISAPI, Motion Gap bounds how long to wait for a missing inactive message, including when the event stream is quiet. Captured After keeps the same motion writer open after the inferred end; a new active during that period continues the same clip and notifications rather than starting a second clip with overlapping pre-buffer. With Motion Gap 10s and Captured After 5s, the maximum quiet tail is about 15s. The existing motion recorder persists the normalized labels in `ai_metadata` so Timeline object filters and notifications work for both camera-native and server AI events. `event_source` on saved clips identifies the provider; bounded optional timestamp/channel/rule/region fields are stored in `event_metadata`. New video events use the actual stop time and probed media duration for Timeline start/end instead of labeling the movie-end webhook time as the start. Existing historical events are unchanged. The admin-only camera provider status endpoint reports connection state, observed labels and last event type without exposing host, credentials or raw payload.

To add another provider, implement a bounded connection loop that emits `CameraEvent`, keep vendor parsing inside its provider module, route only the selected provider to the existing engine trigger, and extend schema/configuration validation and parser/lifecycle tests. Do not open another RTSP stream or write clips inside a provider.
